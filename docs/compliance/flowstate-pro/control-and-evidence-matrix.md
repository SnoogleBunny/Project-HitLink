# Flowstate Pro control and evidence matrix

**Status:** DRAFT control design; no row asserts implementation, operating effectiveness, legal review, or production approval  
**Scope:** Flowstate Pro only  
**Authority:** `README.md`, `decision-register-and-open-items.md`, `legal-applicability-matrix.md`, the Pro PRD/design documents when created, and the detailed implementation plan

## 1. How to read this matrix

- **Requirement** states the outcome to satisfy. **Control** is the proposed mechanism. **Test** is the minimum repeatable check. **Required evidence** is what a reviewer must inspect.
- **Current evidence** is deliberately explicit. `None recorded` means no artifact has been inspected or accepted; it does not mean the control failed or passed.
- `SPECIFIED` means only that this document defines the control. It does not mean `IMPLEMENTED`, `TECHNICALLY_VERIFIED`, `OPERATIONALLY_EXERCISED`, `EVIDENCE_COMPLETE`, `LEGALLY_REVIEWED`, or `APPROVED_FOR_PROFILE`.
- A row reaches `EVIDENCE_COMPLETE` only after the exact build/deployment/profile has implementation evidence, repeatable test output, operating evidence where applicable, reviewer identity, date, and protected artifact reference. Code and tests cannot satisfy legal, contractual, personnel, training, incident, vendor, or executive gates by themselves.
- Required contracts, legal advice, personnel files, incident materials, secrets, production exports, and assessor workpapers are not committed. The repository stores approved templates, non-sensitive metadata, hashes/manifests where suitable, and access-controlled evidence references.
- If a requirement is not applicable, qualified reviewers must record scope, reason, source, approver, profile/version, and review date before assigning `NOT_APPLICABLE`.

## 2. Control ownership

| Owner label | Accountable function |
|---|---|
| Executive risk owner | Accepts residual business risk, resources the program, approves launch/claims with required reviewers |
| Security Official | HIPAA Security Rule accountability, security program, risk analysis, access and technical safeguard governance |
| Privacy lead | Privacy program, customer responsibility matrices, rights, purpose/consent, incident privacy coordination |
| Legal counsel | Customer/profile applicability and legal-policy determinations; not delegated to software |
| Incident commander | Operational command, clocks, containment, evidence, communications coordination |
| Platform/Operations | Infrastructure, identity operations, monitoring, backup/restore, DR, deployment and access execution |
| Engineering | Implements approved application controls and maintains tests/static gates |
| QA/Assurance | Independent verification, negative testing, evidence completeness and release reconciliation |
| Vendor owner | Due diligence, agreement/renewal/region/support commitments and vendor inventory |
| Customer record authority | Customer decisions on custody/control, clinical records, representatives, rights and disclosures under approved allocation |

At least one named natural person must fill each required accountable role before production. One person may hold compatible roles in a small organization, but the independent second approver cannot approve their own high-risk action or risk acceptance.

## 4. Launch evidence gate

A profile may be proposed for production only when all applicable matrix rows have:

1. a named owner and reviewer;
2. an approved requirement/control version;
3. actual implementation/configuration evidence from the exact candidate and environment;
4. repeatable passing test output and failure disposition;
5. operating evidence for human and recurring controls;
6. executed agreement and counsel decision references where applicable;
7. no unresolved `BLOCKED` dependency;
8. a current independent review and risk disposition;
9. an approved claim set scoped no broader than the evidence; and
10. explicit Security/Privacy, Legal, QA/Assurance, executive, and customer-profile approvals required by the decision register.

The gate result must name the profile, tenant cohort, jurisdictions, services, regions, vendors, versions, evidence manifest, approvers, effective date, expiry/review date, exclusions, and rollback owner. Approval of one profile does not approve another.

## 5. Evidence-state transition

`DRAFT` → `SPECIFIED` → `IMPLEMENTED` → `TECHNICALLY_VERIFIED` → `OPERATIONALLY_EXERCISED` → `EVIDENCE_COMPLETE`

Legal and profile decisions run as separate necessary dimensions: `COUNSEL_REVIEW_REQUIRED` → `LEGALLY_REVIEWED`, and `OWNER_APPROVAL_REQUIRED` → `APPROVED_FOR_PROFILE`. A control is launch-ready only when all applicable technical, operational, legal, owner, and evidence dimensions are complete. `BLOCKED`, `SUPERSEDED`, and `NOT_APPLICABLE` require explicit reason and approval metadata; they are never inferred from silence.
